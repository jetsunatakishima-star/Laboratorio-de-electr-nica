# Laboratorio-de-electronica
# INFORME DEL SISTEMA DE GESTIÓN DE INVENTARIO DEL LABORATORIO DE ELECTRÓNICA

1. Introducción y ObjetivosEl presente informe detalla el diseño, la estructura de clases, la relación directa entre el modelado conceptual (Diagramas UML) y el código fuente en Python, así como la evolución tecnológica del sistema de persistencia hacia una base de datos relacional con SQLite. El software está diseñado para gestionar eficientemente el inventario de un laboratorio de electrónica, implementando control de accesos por roles y tipificación estricta de componentes.   2. Vinculación Directa: Del Diagrama UML al Código FuenteEl diseño orientado a objetos del sistema se visualiza claramente en el diagrama de clases. A continuación, se detalla cómo cada componente gráfico y relación del diagrama se traduce de forma exacta en la implementación en Python:   2.1 Jerarquía de Componentes ElectrónicosClase Padre (ComponenteElectronico): En el diagrama, esta clase central define los atributos comunes de cualquier inventario (id, nombre, cantidad, ubicacion) y las operaciones globales (obtener_detalles, to_string). En el código, esto se implementa mediante el constructor __init__ y los métodos base de la clase principal, de la cual heredan todas las demás mediante la función super().__init__().   Clases Hijas (Especializaciones): El diagrama muestra flechas de herencia hacia las subclases organizadas por categorías:   Pasivos: Resistencia (valor_ohmios, tolerancia), Condensador (capacitancia, voltaje_max) y Bobina (etiquetada como Bocina en el esquema conceptual) (inductancia, corriente_max).Activos: Diodo (tipo_diodo, corriente_max), Transistor (tipo_transistor, encapsulado) y CircuitoIntegrado (numero_pines, funcion).Placas y Sistemas: Microcontrolador (voltaje_operacion, velocidad_reloj) y Sensor (magnitud_medida, interfaz).Instrumentación: InstrumentoLab (marca, precision_o_rango).Traducción en Código: Cada una de estas cajas del diagrama UML corresponde exactamente a una clase hija en Python que extiende ComponenteElectronico, agregando sus atributos específicos en su propio constructor y sobrescribiendo (polimorfismo) los métodos obtener_detalles() y get_db_data().2.2 Módulo de Usuarios y Control de AccesosClase Base Usuario: El diagrama expone una entidad superior con los atributos de identificación (usuario, carnet) y el método abstracto mostrar_menu_rol(sistema).   Subclases de Roles:Estudiante: Hereda de Usuario e incorpora el atributo específico carrera. Su lógica en código despliega un menú restringido exclusivamente a la visualización de inventarios.   Encargado: Hereda de Usuario e incorpora el atributo cubiculo. Su menú de opciones en el código otorga privilegios de escritura, permitiendo registrar componentes específicos de cualquier tipo y ejecutar bajas por ID.   2.3 Subsistema de Persistencia y Controlador (SistemaInventario)Módulo de Persistencia: En el diagrama original, la persistencia se concebía acoplada conceptualmente a un archivo de texto plano (txt) mediante un bloque administrador con métodos como agregar_item(), eliminar_item(), mostrar_inventario(), guardar_en_archivo() y cargar_desde_archivo().   Evolución en Código: Esta estructura lógica evolucionó en el sistema final hacia la clase SistemaInventario. Aunque el diagrama conceptual sugería un archivo plano (txt), la refactorización actual reemplazó el almacenamiento de texto por un motor relacional en SQLite (inventario.db), manteniendo intacta la interfaz de métodos del controlador para garantizar un acoplamiento limpio.3. Arquitectura de Persistencia con SQLitePara solventar las limitaciones de los archivos planos en cuanto a integridad referencial y consultas estructuradas, el sistema implementa una tabla relacional unificada:Estructura de la Tabla (componentes):Se crea de manera automatizada mediante el método inicializar_db() con la siguiente estructura relacional:SQLCREATE TABLE IF NOT EXISTS componentes
   (
    id TEXT PRIMARY KEY,
    tipo TEXT,
    nombre TEXT,
    cantidad INTEGER,
    ubicacion TEXT,
    attr1 TEXT,
    attr2 TEXT
)
Mapeo Polimórfico de Atributos:Dado que cada clase hija posee atributos de naturaleza distinta (por ejemplo, los Ohmios de una resistencia frente a los Pines de un circuito integrado), el sistema implementa el método get_db_data(). Este método devuelve una tupla con el tipo de componente y dos atributos genéricos (attr1 y attr2), permitiendo almacenar objetos heterogéneos de manera uniforme en la base de datos sin alterar el principio de diseño orientado a objetos.Reconstrucción Dinámica:Cuando el método mostrar_inventario() consulta la base de datos, utiliza una función de fábrica interna (_crear_instancia()) que lee el campo tipo de cada registro y reconvierte dinámicamente los datos planos de SQLite en instancias de objetos de Python con sus respectivas clases hijas.4. ConclusionesLa integración del diseño basado en el diagrama de clases UML con una arquitectura orientada a objetos en Python garantiza un código altamente modular, extensible y fácil de mantener. La posterior adopción de SQLite eleva la robustez del software, transformando un prototipo académico de archivos planos en una solución de inventario persistente, segura y preparada para crecer ante nuevas necesidades de laboratorio.
